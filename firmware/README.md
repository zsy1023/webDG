# 假郊狼主机固件（ESP32）—— T1 收尾

在 ESP32 上**复刻 DG-LAB 郊狼主机 3.0 的 BLE 外设**（广播名 `47L121000` + 真机 GATT 全表），
把控制者手机 App 的所有写入经**串口**转交给 PC 侧的 `agent/nodes/sim_coyote`，
并把 PC 侧回的强度回包从 BLE 推回 App。

```
控制者手机 DG-LAB App ──BLE──> ESP32（本固件）──串口 115200──> PC 侧 sim_coyote
                                    ▲                                │
                                    └──────── B1 强度回包 ────────────┘
```

---

## 1. 硬件与接线

| 项 | 值 |
|---|---|
| 板子 | 任意 ESP32 开发板（本机实测 **ESP32-D0WD-V3**，BLE 4.2，CH340 USB 转串口） |
| 接线 | **只要一根 USB 数据线**接电脑（既是供电也是数据+烧写）。BLE 天线板载，不需要任何外设 |
| 串口 | 插上后在设备管理器里出现一个 COM 口（本机是 **COM18**，`USB VID:PID=1A86:7523`） |
| 与手机的距离 | 1~10 米内正常；App 走 BLE，跟串口无关 |

> ⚠️ 本机 `COM5`/`COM6` 是**蓝牙虚拟串口**——能打开成功但**一个字节都收不到**。
> 填错口会"看起来正常但没数据"。用 `python -m agent.nodes.sim_coyote.esp32_link` 列串口，
> 它会把蓝牙虚拟口标出来、并标出"像 ESP32 开发板"的口。

## 2. 编译 / 烧写 / 观察日志

```powershell
# 依赖都已在开发机上备好（platform-espressif32@6.4.0 + arduino core 2.0.11 + xtensa 工具链）
cd firmware
pio run                                      # 编译
pio run -t upload --upload-port COM18        # 烧写（把 COM18 换成你的口）
pio device monitor -p COM18 -b 115200        # 看 '#" 日志（可选）
```

> ⚠️ **串口是独占的**：烧写/监视之前，先停掉 PC 侧的 sim_coyote（否则打不开口，或抢字节）。

## 3. ★ 串口帧协议（**契约，两边都照这个来**）

PC 侧实现见 `agent/nodes/sim_coyote/transport.py` 的 `Esp32Peripheral`；
固件侧见 `src/main.cpp` 顶部常量。**改这里必须两边同时改。**

### 3.1 帧（HEAD 字节定长分帧，无长度前缀、无校验）

| 方向 | 帧 | 含义 |
|---|---|---|
| ESP32 → PC | `0xB0` + 19B（共 **20** 字节） | App 的 `B0` 指令，**原样透传** |
| ESP32 → PC | `0xBF` + 6B（共 **7** 字节） | App 的 `BF` 指令，**原样透传** |
| ESP32 → PC | `0xCC`（**1** 字节） | App 已连上 |
| ESP32 → PC | `0xCD`（**1** 字节） | App 已断开 |
| PC → ESP32 | `0xB1` + 3B（共 **4** 字节） | 强度回包，固件 notify 到 `0x150B` |
| PC → ESP32 | `0xCE`（**1** 字节） | 心跳（固件回一条 `#` 日志行，用于"对面到底是不是假主机"的在线探测） |

* **不解析、不重组**：`B0`/`BF` 就是 App 写进来的那 20/7 个字节，原样搬到串口；
  语义解析全在 PC 侧 `protocol.py`（那里有 28 项单测，含与真机逐条对拍）。
* 长度/帧头不符合的写入**不进链路**（避免污染 PC 侧的定长分帧），但会打日志记录下来。
* 固定波特率 **115200 8N1**（PC 侧可配，两边要一致）。

### 3.2 日志约定（和二进制帧共存的办法）

固件所有人类可读日志都是 **`#` 开头 + `\n` 结尾**，PC 侧在分帧时**整行丢弃**：

```
#假郊狼主机启动：name=47L121000 bt_mac=EC:E3:34:A9:13:0E
#App 已连接（conn_id=0）
#0x150B 已被订阅 → 发设备握手 53 00 34 A9 13 0E
#B1 ← 主机：B1 01 0A 00
#stats up=736 drops=8 down_bytes=210 b1=52 unknown=0 conn=1 sub=1
```

`#`（`0x23`）**不在帧头集合里**，所以两者不会互相误判；
帧体内部的 `0x0A` 也不会被当成换行（只在"等帧头"时才按行丢弃）。
这条约定让"日志"和"协议"共用同一个 UART0 而互不干扰 —— **别往串口打不带 `#` 的文本**。

### 3.3 故障与保护

* **半帧看门狗**：收到帧头后 200ms 还没凑齐 → 丢弃重同步（否则丢一个字节会把下行永久卡死）。
* **上行缓冲兜底**：PC 侧缓冲超过 4096 字节 → 清空重同步。
* **在线探测**：PC 侧打开串口后发 `0xCE`，收不到任何帧/日志行就**明确报错**
  （"打开成功但对面没应答"= 填错口/没烧固件），不会静默假死。
* **断线重连**：PC 侧拔线/复位/端口被抢占都会自动退避重连。

## 4. 复刻的 GATT 表（对照 `docs/research/郊狼真机GATT实测.md`）

| 服务 | 特征 | 属性 | 值 / 说明 |
|---|---|---|---|
| `0x1800`（协议栈内建） | `0x2A00` 设备名 | read, write | `47L121000` |
| | `0x2A01` / `0x2AA6` | read | Appearance / 地址解析 |
| `0x1801`（协议栈内建） | `0x2A05` | indicate | Service Changed |
| `0x180C` | `0x150A` | **write-without-response** | App 的所有指令（不是普通 WRITE！） |
| | `0x150B` | notify | 我们的所有回包（`B1` 等） |
| `0x180A` | `0x1500` | read, notify | 电量，1 字节百分比（`0x64` = 100%） |
| | `0x1501` | read | `0c 03` —— **App 靠它判定协议 V3，必须照回** |
| | `0x1502` | read | 6 字节本机 MAC |
| | `0x2A25` | read | `"CEB3%Q"` + MAC（12 字节） |
| | `0x2A59` | read, notify | 10 字节输出状态回读（见 §6 近似说明） |
| `0x2003` | `0x0007` / `0x0008` | write / read+notify | 用途未知，照真机提供 |
| `0x2004` | `0x0009` | read, write | 同上 |
| `0xFE59` | Nordic DFU | — | **不复刻**（真机有，App 不需要） |

行为细节（都是真机实测，不是照官方文档）：

* 广播里**只有名字**，不带服务 UUID、不带厂商数据；
* 订阅 `0x150B` 成功后**立刻**发 6 字节 `53 00 <MAC 后 4 字节>`；
* 断开后**自动重新广播**（否则手机再也搜不到）。

## 5. 延迟

一次"App 调强度 → 界面回显"要经过：
`BLE 往返` + `串口上行` + `PC 解析/回包` + `串口下行` + `BLE 通知`。

本机实测（2026-10-04）：

| 段 | 耗时 |
|---|---|
| 串口回路（PC 写 → 固件处理 → PC 收到），**优化后** | **p50 4.5 ms** |
| 同上，优化前（PC 侧 `read(256)`） | p50 87.9 ms ← 曾经的"反应慢"元凶 |

固件侧为此做的：`loop()` 轮询 1ms、连接后请求 15~30ms 的快速连接参数、
状态日志 8 秒一条（少占串口）。

## 6. 已知问题 / 待办

1. **`0x2A59` 是近似复刻**：真机的精确编码规则仍未解出（只知道它随 `B0` 的波形变）。
   当前实现：字节 0-1 恒 `01 01`、字节 2/3 跟 A/B 通道的波形强度走、其余保持基线。
   App 订阅了它，目前工作正常；要精确复刻需拿真机多测几组。
2. **`0x1800` 下缺 `0x2A04`（首选连接参数）**：该特征由 ESP-IDF 协议栈按编译配置提供，
   当前 Arduino core 的预编译库没开，补它要重编 IDF。所以改用"连接后主动请求快速连接参数"达到同样目的。
3. **App 还会往 `0x150A` 写非 B0/BF 的数据**（实测每 20 秒左右一条，形如
   `BC 04 32 32 32 1E 50 96 32`），按契约丢弃并记日志。语义未知，暂不影响功能。
4. **未加密链路上 `0x1500`/`0x2A59` 的订阅**：真机在 Windows 侧也会被拒（`Access Denied`），
   是链路/主机侧的限制；手机 App 那边不受影响。
