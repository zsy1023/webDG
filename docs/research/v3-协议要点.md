# DG-LAB（郊狼）V3 WebSocket 协议要点

> 调研来源（均为工作区内源码/文档，未修改）：
> - `reference/dglab-websocket-server/v3-server.ts`（V3 中继服务端，1154 行）
> - `reference/dglab-kit/src/socket/v3/index.ts` 与同目录 `types.ts`（V3 客户端 SDK）
> - `reference/dglab-websocket-server/README.md` 的 V3 章节
> - `reference/dglab-kit/README.md` 的 V3 章节
> - `reference/dglab-websocket-server/.env.example`
>
> 文中形如 `v3-server.ts:120` 的标注，指向该结论的源码出处（相对 `reference/`）。

V3 是**旧协议**，模型为 **1 控制方 : 1 被控方（APP）** 的点对点配对，服务端只做「两端连接 + 配对 + 指令翻译 + 波形拆包定时下发」的中继。服务端**会解析并转换**业务指令（强度 / 清除 / 波形），这一点与 V4 的纯数据透传截然不同。

---

## 1. 连接与配对（bind）流程

### 1.1 连接即分配 clientId

任一客户端连上 V3 服务后，服务端用 `crypto.randomUUID()` 生成 `clientId`，并**立即**下发一个「初始 bind」帧（`v3-server.ts:98-125`）：

```json
{
  "type": "bind",
  "clientId": "当前连接随机生成ID",
  "targetId": "",
  "message": "targetId"
}
```

客户端 SDK 收到这种 `targetId` 为空串的 bind，即视为「连接阶段完成」，把 `clientId` 记为控制方 `targetId`，进入 `WaitingForPeer`（`v3/index.ts:167-170, 241-246`）。二维码即可用这个 `clientId` 生成（`v3/index.ts:242`）。

### 1.2 两条配对路径

**路径 A：控制端主动发 bind 帧绑定**（`v3-server.ts:364-389`）

控制端拿到 APP 端 clientId 后发送：

```json
{
  "type": "bind",
  "clientId": "控制端 clientId",
  "targetId": "APP 端 clientId",
  "message": "targetId"
}
```

**路径 B：APP 端带 targetId 直连指定控制端**（`v3-server.ts:100-150, 1118-1138`）

APP 端连接时 URL 携带目标控制方 ID，服务端解析顺序为 `?targetId=` → `?tid=` → 路径末段 `/{targetId}`（`v3-server.ts:1124-1130`）。若 `targetId` 无效（不存在/已绑定/非 OPEN），服务端直接下发错误并关闭（见 §6）。有效则自动配对。

### 1.3 配对成功 = message:"200"

配对逻辑在 `pair()`（`v3-server.ts:797-817`）。成功时双方都收到（路径 A：`v3-server.ts:387-388`；路径 B：`v3-server.ts:142-149`）：

```json
{
  "type": "bind",
  "clientId": "控制端 clientId",
  "targetId": "APP 端 clientId",
  "message": "200"
}
```

- **`message` 字段承载结果码**：`"200"` = 配对成功；`"401"` = 目标无效 / 不能绑定自己；`"400"` = 已被绑定。
- 配对成功会**取消未配对空闲计时器**（`v3-server.ts:813-814`），进入 `Paired` 状态。
- 重复绑定同一对（`isPaired` 成立）视为幂等，仍返回 200（`v3-server.ts:802-805`）。
- 服务端维护双向映射 `webToApp` / `appToWeb` 以便 O(1) 查找对端（`v3-server.ts:89-90, 810-812`）。

SDK 侧以「`targetId` 非空且 `message === '200'`」判定配对完成，记录 `pairedClientId`，派发 `client-attached`（`v3/index.ts:172-176, 253-260`）。

### 1.4 连接保活与超时

| 机制 | 默认值 | 说明 | 来源 |
| --- | --- | --- | --- |
| 心跳间隔 | `60000` ms | 服务端定时向所有连接发 `heartbeat` 帧，`message:"200"` | `v3-server.ts:6, 253-272` |
| 空闲超时 | `300000` ms（5 分钟） | 仅对**未配对**连接生效，超时后发 `error:idle_timeout` 并 `close(1000)` | `v3-server.ts:8, 274-307` |
| 心跳上行 | — | 客户端发 `type=heartbeat` 的消息，服务端**忽略**不转发 | `v3-server.ts:207-209` |

连接建立后校验 `validateSource()`：报文 `clientId` 或 `targetId` 必须等于发送方连接自身的 ID，否则 404（`v3-server.ts:356-362, 176-183`）。

## 2. 全部消息类型与字段

### 2.1 通用报文字段

服务端解析出的消息结构（`v3-server.ts:44-53`）；前 4 个字段为**必填**（`v3-server.ts:335-351`）：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `type` | `string \| number` | ✅ | 消息类型，决定服务端分流；可为 `bind` / `clientMsg` / `heartbeat` / 数字 `1~4` / 字符串数字 `"1"~"4"` |
| `clientId` | `string`（非空） | ✅ | 控制端 ID |
| `targetId` | `string`（非空） | ✅ | APP 端 ID |
| `message` | `string` | ✅ | 消息内容：业务指令 / 波形数据 / APP 回传 |
| `channel` | `string \| number` | 视类型 | 通道：`1`/`"1"`/`"A"`/`"a"` 或 `2`/`"2"`/`"B"`/`"b"` |
| `strength` | `number` | 视类型 | 强度值（type 3/4 使用） |
| `time` | `number` | 视类型 | 波形持续秒数（type=clientMsg 使用） |

字段校验失败统一回 `error:403`（`v3-server.ts:319-354`，见 §6）。

### 2.2 服务端/客户端下行帧类型

| 帧 `type` | 方向 | 说明 | 来源 |
| --- | --- | --- | --- |
| `bind` | 服务端→端 | 连接分配 / 配对结果 | `v3-server.ts:120, 142, 374` |
| `msg` | 双向 | 转发指令、强度、波形包、APP 回传 | `v3-server.ts:428, 604` |
| `notify` | 服务端→控制端 | 「发送完毕」「波形被覆盖」提示 | `v3-server.ts:651, 789` |
| `heartbeat` | 服务端→端 | 心跳 | `v3-server.ts:263` |
| `break` | 服务端→端 | 对端断开通知（`message:"209"`） | `v3-server.ts:236` |
| `error` | 服务端→端 | 错误码（见 §6） | `v3-server.ts:892` |
| `clientMsg` | 控制端→服务端 | 波形下发（服务端拆包，见 §4） | `v3-server.ts:203` |

> SDK 侧帧类型定义见 `v3/types.ts:6-59`（`V3BindFrame` / `V3MessageFrame` / `V3BreakFrame` / `V3ErrorFrame` / `V3HeartbeatFrame`）。

### 2.3 服务端消息分流顺序（`v3-server.ts:185-211`，重要）

到达消息按**优先级**依次判断：`bind` → 若 `message` 以 `feedback`/`strength` 开头则转发 → 数字 `type` 1/2/3 → 数字 `type` 4 → `clientMsg` → `heartbeat`（忽略）→ 其余一律 `forwardMessage`。

> ⚠️ 关键点：`isAppReportMessage()`（`v3-server.ts:1053-1054`）判断在数字 type 判断**之前**。因此只要 `message` 以 `strength` 或 `feedback` 开头，即使带数字 type，也会走「直接转发」而非强度处理逻辑。

## 3. 强度控制

### 3.1 type 1/2/3：增减与设置（`handleStrengthAdjust`，`v3-server.ts:391-442`）

前置校验：**发送方必须是控制端**（`isWebSender`，`clientId === senderId`，`v3-server.ts:865-870`）→ 否则 404；必须已配对（`isPaired`）→ 否则 402；`channel` 必须可解析（默认回退通道 1）→ 否则 406。

服务端把 type 翻译成 APP 可识别的字符串，`sendType = type - 1`（`v3-server.ts:424`），再带 `strength`（仅 type 3 取真实值，否则固定 1）拼出：

```ts
`strength-${channel.number}+${sendType}+${strength}`   // v3-server.ts:427
```

| 控制端 `type` | 含义 | 服务端转发给 APP 的 `message` |
| --- | --- | --- |
| `1` | 减少强度 | `strength-<通道>+0+1` |
| `2` | 增加强度 | `strength-<通道>+1+1` |
| `3` | 设置到指定 `strength` | `strength-<通道>+2+<strength>` |

`<通道>` 为数字 `1`（A）或 `2`（B）。转发帧形如（`v3-server.ts:428-433`）：

```json
{
  "type": "msg",
  "clientId": "控制端 clientId",
  "targetId": "APP 端 clientId",
  "message": "strength-1+2+20"
}
```

SDK 侧 `addStrength()` / `reduceStrength()` 走 type 2/1，`setStrength()` 走 type 3（`v3/index.ts:63-105`）。

### 3.2 type 4：指定强度 / 清除（`handleCustomStrength`，`v3-server.ts:444-509`）

同一套前置校验后，按 `message` 是否含 `"clear"` 分支：

| 控制端消息 | 服务端转发给 APP | 附加动作 |
| --- | --- | --- |
| `message` 含 `clear` | `clear-<通道>` | 清除该通道定时器 + 向控制端回 `notify:发送完毕`（`v3-server.ts:475-492`） |
| `message` 不含 `clear` | `strength-<通道>+2+<strength>` | 设置指定通道强度（`v3-server.ts:495-508`） |

SDK 侧 `clearPulse()` 发 type 4 + `message:'clear'`（`v3/index.ts:112-119`）。

### 3.3 通道归一化（`normalizeChannel`，`v3-server.ts:930-944`）

| 输入 | 归一化结果 |
| --- | --- |
| `1` / `"1"` / `"A"` / `"a"` | A 通道，number = `1` |
| `2` / `"2"` / `"B"` / `"b"` | B 通道，number = `2` |
| 其他 | 无效 → 406 |

`channel` 在强度处理中可缺省（回退通道 A，`v3-server.ts:413, 465`），但在波形消息中**必填**（`v3-server.ts:532-540`）。

## 4. 波形消息 `type=clientMsg` 的拆包算法

处理入口 `handleClientMessage`（`v3-server.ts:511-582`），拆包核心 `buildPulseSequence`（`v3-server.ts:946-985`）。

### 4.1 输入

```json
{
  "type": "clientMsg",
  "clientId": "控制端 clientId",
  "targetId": "APP 端 clientId",
  "channel": "A",
  "time": 5,
  "message": "A:[\"0A0A0A0A00000000\",\"0A0A0A0A64646464\"]"
}
```

> SDK `sendPulse()` 生成的 `message` 即 `${channel}:${JSON.stringify(data)}`（`v3/index.ts:126-138`）；标准波形帧为 16 位十六进制字符串（8 字节 = 4 个 A 强度 + 4 个 B 强度），数组每帧按 `100ms` 计（`README.md:432`；帧格式示例见 `dglab-bluetooth-protocol/coyote/v3/example.md`）。

### 4.2 拆包公式

设 `SPS = DEFAULT_PUNISHMENT_TIME`（每秒发送包数），`time` 为波形秒数：

| 量 | 公式 | 来源 |
| --- | --- | --- |
| 发送包数 `packetCount` | `max(1, time * SPS)` | `v3-server.ts:952` |
| 发送间隔 | `1000 / SPS` ms | `v3-server.ts:557` |
| 总帧数 `totalFrames` | `max(1, time * 10)`（每帧 100ms） | `v3-server.ts:971` |
| 每包帧数 | ≈ `10 / SPS`（把总帧数均分成 packetCount 块） | `v3-server.ts:1024-1029` |

即 `README.md:434-439` 总结的：

```text
总帧数   = time * 10
发送包数 = DEFAULT_PUNISHMENT_TIME * time
发送间隔 = 1000 / DEFAULT_PUNISHMENT_TIME ms
每包帧数 ≈ 10 / DEFAULT_PUNISHMENT_TIME
```

### 4.3 序列构造与两种分支

`parsePulseMessage`（`v3-server.ts:987-1012`）先尝试解析 `message` 中 `:` 之后的 JSON：必须是**非空数组且每项为 16 位十六进制**字符串，否则视为「不可解析」。

- **可解析（标准波形）**：帧数组先经 `fitFramesToLength` 循环补齐/截断到 `totalFrames`（`v3-server.ts:1014-1022`），再由 `splitFrames` 均分成 `packetCount` 块（`v3-server.ts:1024-1029`），每包生成：

  ```ts
  `pulse-${channel}:${JSON.stringify(frames)}`   // v3-server.ts:976
  ```

- **不可解析（历史自定义字符串）**：按原始内容透传重复，每包为 `pulse-${data.message}`（`v3-server.ts:960-968`）。

### 4.4 下发定时队列

`queuePulse`（`v3-server.ts:631-681`）+ `startPulse`（`v3-server.ts:683-748`）：

1. 若同一 `clientId + channel` 已有在发任务（key = `clientId:channel`，`v3-server.ts:1056-1057`）→ 先 `clearTimer`，向 APP 发 `clear-<通道>`，向控制端发 `notify:"当前通道X有正在发送的消息，覆盖之前的消息"`，延迟 `PULSE_REPLACE_DELAY_MS = 150 ms` 再启动新序列（`v3-server.ts:641-670`）。
2. 立即发**第 1 包**，之后 `setInterval(intervalMs)` 逐包发送（`v3-server.ts:711-745`）。目标断开则停止（`v3-server.ts:723-727`）。
3. 全部发完后向控制端发 `notify`（`notifyDone`，`v3-server.ts:784-795`）：

```json
{ "type": "notify", "clientId": "控制端 clientId", "targetId": "APP 端 clientId", "message": "发送完毕" }
```

### 4.5 两个环境变量的作用（`v3-server.ts:9-15, 1031-1035, 1043-1046`）

| 环境变量 | 默认值 | 作用 |
| --- | --- | --- |
| `DEFAULT_PUNISHMENT_TIME` | `1` | **每秒发送的波形包数**（SPS）。经 `normalizeSendsPerSecond` 取整并 **clamp 到 1~10**（>10 按 10 计，等于每帧最小 100ms）；`README.md:441` 亦确认此上限 |
| `DEFAULT_PUNISHMENT_DURATION` | `5` | **波形默认持续秒数**。仅当请求缺 `time` 或 `time ≤ 0` 时作为回退值（`normalizePositiveInteger`，`v3-server.ts:550-553`） |

`.env.example:15-17` 提供默认示例值。二者都可用环境变量覆盖（`numberFromEnv`，`v3-server.ts:1069-1072`）。

## 5. APP 端回传：`feedback-*` 与 `strength-*`

### 5.1 服务端处理（`v3-server.ts:191-194, 584-629, 1053-1054`）

APP 上行 `message` 以 `feedback` 或 `strength` 开头即命中 `isAppReportMessage`，直接 `forwardMessage` 转发给控制端，**不改写 message**。转发时若 `type === 'msg'` 且发送方属于 `appToWeb`（即 APP 发来），会**交换 clientId / targetId**（`v3-server.ts:600-609`）。

APP→控制端回传示例（`README.md:449-465`）：

```json
{ "type": "msg", "clientId": "控制端 clientId", "targetId": "APP 端 clientId", "message": "feedback-1" }
```

### 5.2 客户端 SDK 解析（`v3/index.ts:266-347`）

| 回传 `message` | 解析结果 |
| --- | --- |
| `feedback-<n>` | 派发 `action` 事件，值为数字 `n`（`v3/index.ts:288-293`） |
| `strength-<aStrength>+<bStrength>+<aSoftLimit>+<bSoftLimit>` | 派发 `device` 事件，更新 COYOTE_030 的 A/B 强度与 A/B 软上限（`v3/index.ts:299-347`） |

> ⚠️ **格式不一致提醒**：SDK 解析的强度回传是 **4 段**（`strength-A+B+软限A+软限B`，`v3/index.ts:302`），而 README 示例为 **3 段** `strength-1+2+20`（`README.md:463`）。控制端实现时应以 4 段格式为主、兼容 3 段。服务端仅做透传，不校验段数。

## 6. 错误码与断开消息

### 6.1 错误码（`error` 帧，`message` 字段为码）

| 码 | 含义 | 触发点来源 |
| --- | --- | --- |
| `400` | 连接（任一端）已被绑定 | `pair()`：`v3-server.ts:806-808` |
| `401` | 绑定目标无效，或试图绑定自己 | `pair()`：`v3-server.ts:798-801`（bind 失败回执 `v3-server.ts:381-385`） |
| `402` | 双方未建立配对关系 | 强度/指定强度/波形/转发前校验：`v3-server.ts:409, 461, 528, 593` |
| `403` | 消息格式错误（非 JSON / 缺字段 / 字段类型错 / 空 ID） | `parseProtocolMessage`：`v3-server.ts:329-351` |
| `404` | 目标不存在，或消息来源非法 | `v3-server.ts:181, 401, 437, 453, 505, 520, 545, 616` |
| `405` | **未使用** | 实际代码与 README 均未出现（`v3-server.ts` 全文、`README.md:495-504`）；属保留码 |
| `406` | 通道参数错误 | 强度：`v3-server.ts:419, 471`；波形缺通道：`v3-server.ts:538` |

错误帧结构（`sendError`，`v3-server.ts:882-898`）：

```json
{ "type": "error", "clientId": "…", "targetId": "…", "message": "402" }
```

### 6.2 断开消息 `break`（209）

`onClose`（`v3-server.ts:213-251`）：任一端断开时，清除其定时器、解除配对，并**通知另一端并发起关闭**：

```json
{ "type": "break", "clientId": "配对方 clientId", "targetId": "断开方 clientId", "message": "209" }
```

随后 `pairedClient.ws.close(1000, 'partner_disconnected')`（`v3-server.ts:236-242`）。SDK 收到 `break` 会清空配对、回到 `WaitingForPeer` 并派发 `client-disconnected`（`v3/index.ts:179-191`）。

### 6.3 其他关闭码

| 关闭码 | 场景 | 来源 |
| --- | --- | --- |
| `1000` + `idle_timeout` | 未配对连接空闲超时（先发 `error:idle_timeout`） | `v3-server.ts:299-305` |
| `1000` + `partner_disconnected` | 对端断开导致本端被关闭 | `v3-server.ts:242` |
| `4001` + `invalid_target_id` | 连接时携带的 targetId 无效（`CLOSE_INVALID_TARGET_ID`） | `v3-server.ts:19, 900-907` |

## 7. V3 二维码格式

由控制方 `targetId`（= 连接时服务端分配的 `clientId`）拼接（`README.md:469-478`）：

```ts
const wsUrl = `wss://your-domain.example/${targetId}`;   // 路径末段即 targetId
const qrcode = `https://www.dungeon-lab.com/app-download.php#DGLAB-SOCKET#${encodeURIComponent(wsUrl)}`;
```

- 本地开发用 `ws://127.0.0.1:9999/${targetId}`（公网/HTTPS 页面须 `wss://`）。
- **targetId 传递位置**：APP 端连接时 targetId 可放在**路径末段**，或 query `?targetId=` / `?tid=`（服务端解析优先级 `targetId` → `tid` → pathname 末段，`v3-server.ts:1124-1130`）。因此 V3 二维码推荐的 `wss://host/{targetId}` 形式与路径解析兼容。
- 对比 V4 二维码不同：V4 用 `https://dungeon-lab.cn/s/?v=1&action=socket&url=${encodeURIComponent('wss://…/v4?tid=' + targetId)}`（`README.md:132-137`）。

## 8. V3 与 V4 的关键区别

| 维度 | V3 | V4 |
| --- | --- | --- |
| 配对拓扑 | **1 控制方 : 1 被控方** | **1 控制方 : N 被控方** |
| 默认端口 | `9999`（`v3-server.ts:4`；`README.md:12`） | `9998`（`README.md:11`） |
| 心跳间隔 | `60000` ms（`v3-server.ts:6`） | `30000` ms（`README.md:99`） |
| 被控方接入方式 | 带 `?targetId=` / `?tid=` / `/{id}`，或由控制端发 bind 帧 | 带 `tid=控制方clientId` |
| 连接/接入帧 | `bind`（分配 clientId、message `"200"` 配对） | `hello` / `client_attached` / `controller_attached` |
| 断帧类型 | `break`（`message:"209"`） | `controller_disconnected` / `client_disconnected` |
| 业务消息承载 | `clientId`/`targetId`/`message` 平铺，服务端**解析并翻译指令**（strength / clear / pulse 拆包） | `type`/`clientId`/`data`，业务数据**原样透传**，服务端不解析设备指令（`README.md:128`） |
| 错误码 | 数字 `400~404/406`（字符串） | 字符串 `bad_request` / `client_not_found` / `controller_not_found`（`README.md:249-253`） |
| 断开码 | `209`（break）、`4001`（invalid_target_id） | `4000` / `4001` / `4002`（`README.md:257-261`） |
| 二维码 | `https://www.dungeon-lab.com/app-download.php#DGLAB-SOCKET#<encoded wss://host/targetId>` | `https://dungeon-lab.cn/s/?v=1&action=socket&url=<encoded wss://host/v4?tid=targetId>` |
| SDK 开关 | `DGLAB_SOCKET_VERSION.V3`（`dglab-kit/README.md:351, 363`） | 默认 |

**实践建议**：新实现优先 V4；V3 仅在兼容旧版控制端 / 旧 APP 时使用，且控制端需自行承担强度写法与波形序列化（建议用 SDK `sendPulse` + 内置波形库，避免手写十六进制帧导致 APP 无法解析，`README.md:443`）。

## 关键结论速览

1. **配对成功以 `bind.message === "200"` 判定**；`400` 已绑定、`401` 目标无效/绑定自己（`v3-server.ts:797-817`）。
2. **强度字符串格式**：服务端把 type 1/2/3/4 翻译成 `strength-通道+{type-1}+强度`（type 4 也可产出 `clear-通道`）（`v3-server.ts:427, 476, 496`）。
3. **波形拆包**：`总帧数=time*10`、`包数=time*SPS`、`间隔=1000/SPS`、每包约 `10/SPS` 帧；不可解析则透传 `pulse-<原始message>`（`v3-server.ts:946-985`）。
4. **`DEFAULT_PUNISHMENT_TIME`（默认 1）= 每秒包数（clamp 1~10）**；`DEFAULT_PUNISHMENT_DURATION`（默认 5）= 缺省波形秒数（`v3-server.ts:9-15`）。
5. **APP 回传 `feedback-*` / `strength-*` 由服务端原样转发**，命中判断在数字 type 之前（`v3-server.ts:191-194, 1053-1054`）。
6. **错误码 400/401/402/403/404/406，无 405**；断开固定 `break{message:"209"}` + 关闭对端（`v3-server.ts:236-242`）。
