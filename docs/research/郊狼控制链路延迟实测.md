# 郊狼控制链路 · 延迟实测

> 2026-10-04 本机实测（脚本：`tools/dev/coyote_latency.py`）。
> 只回答一个问题：**从"点开火"到"真设备有反应"，时间花在哪。**
> 结论一句话：**瓶颈是真郊狼自己的 100ms 帧周期 + 网络段，本机软件部分（≈1ms）可以忽略。**

---

## 一、链路分段

```
web面板 / rules ──① Zenoh command/fire ──> coyote_v4 ──② 组帧+SDK发送 ──>
                 ──③ V4 socket ──> 被控端 App ──④ BLE ──> 真郊狼
```

部署方式有两种（项目都用）：

| 方式 | ③ 那一段是什么 | 影响 |
|---|---|---|
| **控制端自建 relay + 局域网** | 被控 App 直连控制端 `ws://<控制端IP>:9997` | 局域网 RTT ≈ **1ms**；**实测过的就是这种**（`data/t4_pairing.json`） |
| **樱花穿透 / 公网** | 同上，但走公网隧道 | 取决于链路，RTT 通常 **20~100ms** |
| 官方服务器 | App 与控制端各自连 `dungeon-lab.cn` | 多一跳中转 |

> ⚠️ **不要默认"走官方服务器"** —— 我们的架构是**自建 relay / 点对点**，
> 这正是为了把这一段压到最小。

---

## 二、实测数据（本机段 ①②③）

n=15 轮，波形 `EXTRUSTION`，A 通道 800ms，`overlay=True`：

| 段 | min | **p50** | p90 | p99 | max | mean |
|---|---|---|---|---|---|---|
| **L0** Zenoh：`publish command/fire` → 裸订阅者收到 | 0.1 | **0.1** | 0.2 | 0.3 | 0.3 | 0.1 |
| **L1** 端到端本机段：`publish` → 被控方收到开火帧（含 coyote_v4 解析 + 官方 SDK 组帧 + 发送 + 服务端转发） | 0.8 | **1.0** | 1.4 | 2.0 | 2.0 | 1.1 |

*单位：ms。* 被测的"被控方"是 `tools/dev/v4_stub.py` 的 `FakeApp`（它自己会回 `resp`）。

**读法**：
- Zenoh 本机投递 **0.1ms** —— 几乎就是内存队列，节点化架构**没有**引入可感知的延迟代价；
- `command/fire` 落到被控方手上 **1.0ms** —— `coyote_v4` 的解析 + 组帧 + SDK 发送合计 **≈0.9ms**。

> ⚠️ 上面 L0 是**同机**。跨机的 `command/fire` 要经 `bridge`（白名单 + 加密 + Zenoh 传输），
> 那部分延迟 = 网络 RTT，本脚本不覆盖。

## 三、BLE 段（④）：按真机节拍估算 ≈100ms（协调者确认不再单独实测）

真机这次不在广播（不在范围 / 被手机占着），**BLE 段没实测**；经协调者确认，**用估算值即可**。

估算依据（来自 `docs/research/郊狼真机GATT实测.md`）：真机的 `B0` 处理是 **100ms 一个周期**
（协议就规定每 100ms 写一条 `B0`），实测里 `B0` 写下去到 `B1` 回来就在**同一个周期内**完成
（日志里相邻时间戳差 ≈100ms）。

→ **BLE 段的延迟量级 ≈ 100ms，且这是真机硬件节拍决定的，我们改不了。**

（真要精确复测，真机开机放近后跑：`python tools\dev\coyote_ble_latency.py --rounds 15`）

## 四、汇总（当前认知）

| 环节 | 延迟 | 来源 |
|---|---|---|
| ① Zenoh（本机） | **0.1 ms** | ✅ 实测 |
| ② coyote_v4 组帧 + SDK 发送 | **≈0.9 ms** | ✅ 实测 |
| ③ V4 socket → 被控 App（局域网） | **≈1 ms** | ⚠️ 按局域网 RTT 估（实测环境就是局域网自建 relay） |
| ④ App → BLE → 真郊狼 | **≈100 ms** | ⚠️ 按真机 100ms 帧周期估算（协调者确认不再单独实测） |
| **本机可控软件部分合计** | **≈1 ms** | ✅ 实测 |
| **端到端（局域网部署）** | **≈100 ms 量级** | 瓶颈全在 ④ |

**优化空间**：
- ① ② 已经没有优化余地（1ms 级）；
- ③ 想更快只能缩网络路径（局域网 > 穿透 > 官方服务器）；
- ④ 是硬件周期，**只能靠"提前发"**（预判/防抖），不能靠"发得更快"。

## 五、T1 那条链路（App → 假主机）的额外延迟

```
控制者手机 App ─BLE(≈100ms)─> ESP32 ─串口(1~5ms)─> sim_coyote ─raw_v4(0.1ms)─> coyote_v4 …
```

注意**这条链路会叠加两段 BLE**（App→假主机、真 App→真郊狼），且都受 100ms 帧周期限制。
所以"用手机 App 控制"的体感延迟天然比"面板直接开火"高一档 —— 这是方案固有的，不是实现问题。

## 六、怎么复现

```powershell
# 本机段（不需要任何硬件）—— 会起本地 relay + coyote_v4 + 假 App
python tools\dev\coyote_latency.py

# BLE 段（需要真机在范围、且没被手机 App 占着）
python tools\dev\coyote_ble_latency.py --rounds 15
```
