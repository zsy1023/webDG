| v1 的错误 | v2 修正 |
|---|---|

【★ 整条链路 ×2 且可反向】A 端与 B 端跑同一份程序；A 当控制时 B 当被控，反之亦然，

**关键澄清**
- 被控侧郊狼 = **socket v4**（被控者 App 扫码当 V4 被控方，App 再用蓝牙连真主机）
- 控制侧郊狼 = **连到模拟蓝牙郊狼**（App 以为在操作本地硬件，全量指令被截获）
- 判定：**控制端判定 → 被控端纯执行**

### 房间的两种连接方式（你指定的）
| 模式 | 说明 | 数据路径 | 适用 |
|---|---|---|---|
| **M-A 直连** | A 端建房并监听端口 → **樱花 frp** 暴露 → B 端凭房间码接入 | 点对点，不经第三方 | 有公网穿透时，延迟最低 |
| **M-B 中继** | A、B 都连到同一台公共服务器，凭房间码配对 | 经服务器转发（仅密文） | 双方都在 NAT 后、无穿透时 |
| M-C 增强（可选） | WebRTC DataChannel，樱花/Relay 只做信令 | 真 P2P | 后续降延迟优化 |

> 传输层做成**可插拔抽象**（`Transport` 接口），上层 `FeatureFrame` / 惩罚指令协议与传输无关。
> 你先前选的 WebRTC P2P 落在 M-C；M-A/M-B 先跑通（更简单可靠）。

## 四、协议调研结论（已从源码核实，可直接落地）

### 4.1 DG-LAB V4 WebSocket 协议（被控侧驱动郊狼）

来源：`reference/dglab-websocket-server/v4-server.ts`、`reference/dglab-kit/src/socket/v4/*`

> ⚡ **重要更新**：官方已提供 **Python SDK** → `reference/dglab-kit-python/`（`requires-python >= 3.13`，与本项目环境完全匹配）。
> **V4 客户端不需要自己实现** —— 直接用 `DglabSocket` + `COYOTE_WAVEFORMS`，详见 `docs/tasks/T4-郊狼V4控制端.md`。
> 以下协议细节保留用于理解与排障。

**连接与角色**
- 控制方连 `ws(s)://host:9998` → 收 `{"type":"hello","clientId":"<自己的id>"}`
- 被控方连 `ws(s)://host:9998?tid=<控制方clientId>` → 收 `hello` + `{"type":"controller_attached"}`
- 控制方收 `{"type":"client_attached","clientId":"<被控方id>"}`
- 服务端是**纯透传中继**，`data` 层不解析

**控制方 → 被控方**
```json
{ "type":"message", "clientId":"<被控方id>",
  "data":{ "t":"req", "reqId":"1", "m":"device.op",
           "data":{ "s":"<slotId>", "c":0, "t":7, "v":30, "d":3000, "p":0, "im":true } } }
```
**被控方 → 控制方**
```json
{ "t":"resp", "reqId":"1", "result":{...} }                                   // 或 "error":"..."
{ "t":"ev", "ev":"devices.snapshot", "devices":[...] }
{ "t":"ev", "ev":"devices.patch", "added":[...], "removed":[...] }
{ "t":"ev", "ev":"slots.patch", "slots":[{ "slotId":..., "props":{...}, "slotState":{...} }] }
{ "t":"ev", "ev":"custom.action", "action":0 }
```

| 项 | 值 |
|---|---|
| 方法 `m` | `devices.get` / `device.op` / `device.op.clear` / `ping` |
| 动作 `t` | AppendPulseData=`0` / AddIntensity=`3` / SetTempIntensity=`4` / SetIntensity=`7` |
| 通道 `c` | A=`0` / B=`1` |
| 字段 | `s`=slotId, `v`=值/波形帧, `d`=持续ms, `p`=优先级0-2, `im`=替换同类任务 |
| 超时 | 默认 8000ms；`d > 8000` 时自动放宽到 `d+1000` |

**配对二维码**
```
wsUrl  = wss://<域名>/v4?tid=<targetId>
qrcode = https://dungeon-lab.cn/s/?v=1&action=socket&url=<urlencode(wsUrl)>
```
**断开码**：4000=控制方断开踢出被控方／4001=控制方不存在／4002=空闲超时

### 4.2 郊狼 BLE V3 协议（**模拟郊狼必须实现这一层**）

来源：`reference/dglab-bluetooth-protocol/coyote/v3/README.md`

| 服务 UUID | 特征 UUID | 属性 | 用途 |
|---|---|---|---|
| `0x180C` | `0x150A` | WRITE(≤20B) | 所有指令写入 |
| `0x180C` | `0x150B` | NOTIFY(≤20B) | 所有回应/回调 |
| `0x180A` | `0x1500` | READ/NOTIFY(1B) | 电量 |

补全：`0000xxxx-0000-1000-8000-00805f9b34fb`

- `0xB0`（20B，每 100ms 一条，A/B 合并）= `B0` + 序列号(4bit) + 强度解读方式(4bit) + A强度(1B) + B强度(1B) + A频率×4 + A强度×4 + B频率×4 + B强度×4
  - 解读方式（高2bit=A，低2bit=B）：`00`不变 / `01`相对+ / `10`相对- / `11`绝对
  - 强度 `0~200`；频率 `10~240`；波形强度 `0~100`；**4 组 = 100ms（每组 25ms）**
  - 单通道输出：另一通道塞非法强度（如 101）即整组丢弃
- `0xB1`（回应）= `B1` + 序列号 + A实际强度 + B实际强度 —— **App 的强度回显/反控靠它**
- `0xBF`（7B）= `BF` + AB软上限(2B) + AB频率平衡(2B) + AB强度平衡(2B)，断电保存

> **模拟郊狼的核心工作**：实现上述 GATT 服务，接收 App 的 `B0`，正确回 `B1`/电量/`BF`，
> 让 App 认为硬件在线；再把 `B0` 语义（强度+波形）转成 V4 `device.op` 下发对端。

### 4.3 爪印（Paw Prints）BLE 协议

- **与郊狼主机同款 UUID**：`0x180C` / 写 `0x150A` / 通知 `0x150B`
- D0 上报含 **三轴角度 / 加速度 / 外部电压 / 按钮 pressed**
- 支持肩灯（`0x01~0x07`）、主指示灯、灯效序列、随机反应模式（绿灯→限时按下，超时触发事件）
- **你的 zhuaying 已完整实现，M5 直接移植，不重写**

### 4.4 波形数据格式（**V2 / V3 两种，都支持导入**）

| 格式 | 每帧 | 编码 | 时长 |
|---|---|---|---|
| **V3**（推荐） | 8 字节 / 16 hex | `频率×4 + 强度×4`（各 1 字节） | 100 ms |
| **V2** | 3 字节 / 6 hex | **小端 24 位位打包**：`bit4..0=X`、`bit14..5=Y`、`bit19..15=Z` | 100 ms |

- 例：`2D2D2D2D00000000` → V3，频率 `0x2D`×4、强度 `0x00`×4
- V4 下发时用 `options.version` 指定：**2 = V2 帧；省略或 3 = V3 帧**
- BLE 侧需按 §4.2 算法做频率压缩（`10~1000` → `10~240`）
- **官方波形**：`dglab-kit-python` 的 `COYOTE_WAVEFORMS`（24 个）+ `OVC_WAVEFORMS`（负鼠）—— 数量运行时读取，不硬编码
- **官方测试向量**：`reference/dglab-websocket-simple/socket/DG_WAVES_V2_V3_simple.js`
  含 **16 条**波形的 `raw` / `expectedV2` / `expectedV3` 三份对照 → **用于验证导入与转换的正确性**
- 用户自定义波形支持**导入**（JSON / 纯文本，V2/V3 自动识别）→ 见 `docs/tasks/T4-郊狼V4控制端.md` §4.6

## 五、节点化架构（**v3 重大变更**）

> **决策**：中间件用 **Zenoh**；**按功能细切节点**，一个功能一个独立进程。
> 目标：**多路可复用** + **故障隔离** + ROS2 式节点通信。

### 5.1 为什么改（单体的问题）

v2 的 `agent/` 是**单体程序**，有三个硬伤：
1. 摄像头模块崩了 → **郊狼控制也一起没了**
2. 姿态数据要同时给"面板显示"和"判定引擎" → 只能靠函数调用**硬耦合**
3. 加/换一个功能要动整个程序，无法并行开发

节点化之后：
- 每个功能独立进程，**崩一个不影响其他**（supervisor 可自动重启）
- 数据走**主题**，任意多消费者订阅（**复用**）
- 加功能 = 加一个节点，**不改别人**

### 5.7 房间 = key 前缀（**换房间是怎么真的生效的**）

房间不是"一个名字"，而是 key 前缀 `coyotelink/<room>/…`。所以"换房间"这件事，
**改一个变量是不够的**：publisher / subscriber 在**声明时**就把具体的 key 表达式绑死了。

面板上的创建 / 加入 / 离开房间，走的是这条链路：

```
浏览器  op:"room" {action: create|join|leave, code, url}
   │
   ▼
web 节点  ──[command/room]──►  所有节点（含 web 自己）
   │                              │
   │ 回执 {type:"room", ok:true}   ▼
   │                           Node.switch_room(code)
   └── 换完后广播 {type:"hello"}  · 关旧 session → 换 key 前缀 → **重新声明**整套 pub/sub
       （面板上的"后端实际"跟着变）  · 落盘 <data_dir>/room.json（下次起节点直接用它）
```

三个实现要点（都在 `agent/core/node.py`）：

1. **wrapper 身份不变，只换内部的原生对象**。各节点把 Publisher / Subscriber 存进了
   自己的属性（`self._pub_fire` 这种），若重建对象，那些引用全废 —— 所以
   `Publisher.declare(session)` 只重算 key 并换 `_raw`，对象本身不换。
2. **不重跑 `setup()`**。同上：`setup()` 会再建一遍任务与对象。基类记着
   "声明过什么"（`_registrations`），换房间时按它重新声明即可。
3. **切换窗口期丢弃出站消息**（`Node._switching`）。窗口期内 session 正在重开，
   发出去必失败，而失败会被 `_fatal` 判成"节点有未捕获异常"直接打死
   （`device` 的注册表轮询线程、`sim_coyote` 的 2s 轮询都可能正好撞上）。

绕开基类、直接拿原生 session 声明 pub/sub 的节点（`bridge`）要自己实现
`on_room_switched(old, new)` 钩子来重来一遍。

**房间的优先序**（`Config.load`）：`--room` / `$COYOTELINK_ROOM` >
`<data_dir>/room.json`（面板选过的） > `agent/config.toml` 的 `room` > `local`。

### 5.8 一个房间码 = 房间 + 跨机链路 + AEAD 密钥

房间码不只是"房间名"：`bridge` 的链路房间默认跟着业务房间走，AEAD 密钥又由链路房间
经 HKDF 派生 —— 所以**两端各自在面板上选同一个房间码**，房间隔离和跨机加密一次配齐，
不用再单独配 `[bridge] room_code`。

| 情况 | 链路房间 | 加密 |
|---|---|---|
| 面板选了房间码，`[bridge]` 不配 | = 面板那个码 | 自动开，密钥 = `derive_key(码)` |
| `[bridge] room_code = "…"` | 钉死 | 自动开 |
| 房间是默认的 `local` / 人起的弱名（`bedroom`） | 它 | **不加密 + 警告**（那种密钥猜得出来，"看着像加密"比明文更危险） |
| 显式 `encrypt = false` | — | 关（排障看明文） |

⚠️ 房间码约 29 位熵，离线爆破可行 —— 这一层是**挡中继/旁观者**的，不是抗定向攻击；
需要更强机密性就上 Zenoh TLS（见 `agent/nodes/bridge/README.md` §4）。

### 5.5 supervisor（进程管理）

- 独立进程，读 `agent/nodes.toml` 决定启动哪些节点
- 监控子进程，崩溃**自动重启**（带退避，避免疯狂重启）
- **自身崩溃不影响已启动的节点** —— 节点不依赖 supervisor 存活
- 节点健康通过 Zenoh `status/<node>`（liveliness）感知，而非进程轮询

### 5.6 节点框架（`agent/core/`）—— **必须最先实现**

所有节点都依赖它，所以它是新的**关键路径**（任务书 **TF**）：

### 5.8 惩罚模型：**惩罚 = 特定波形"开火"**

惩罚的主要表现是**下发并播放一个指定的波形**，而不是把强度往上堆。落到协议上就是 V4 的
`device.op` + `AppendPulseData`（动作码 `t=0`）：波形帧数组 + 时长发给被控侧郊狼。

```jsonc
{ "m":"device.op",
  "data":{ "s":"<slotId>", "c":0, "t":0, "v":["0A0A0A0A64646464", "..."], "d":2000 } }
```

- 波形来源：`dglab-kit-python` 的 `COYOTE_WAVEFORMS`（官方，**数量运行时读取**）+ **导入的自定义波形**（V2/V3 均可）
- 判定引擎（`node:rules`）的输出 = 往 `command/fire` 发一条 **"开火哪个波形、哪个通道、持续多久"**
- 这与"安全交给 App"自洽：靠**波形选型**而非堆强度，风险面天然更小

### 5.9 强度管理（**真实的复杂点 —— 必须正确处理**）

> 来自真机使用反馈。当前 `fire()` 只做了一半：它把强度**加完就不管了**，不符合真实玩法。

#### 5.9.1 开火是"有时长的"，结束必须把强度降回去

真实玩法：一次开火 = **临时提强度 + 播指定波形**，**时长结束就恢复**。
若只 `add_intensity(+N)` 不回落，强度会**一直停在 N**，下次开火越堆越高 —— 危险，也不是用户预期。

| 方案 | 做法 | 优劣 |
|---|---|---|
| **A（推荐）** | 用 `set_temp_intensity(v, duration)`（V4 动作码 `SetTempIntensity=4`） | App 侧自动回落，无需我们守时；**需实测它对波形的兼容性** |
| B | 自己 `add(+N)` → `duration` 后定时 `add(-N)` | 完全可控，但**网络抖动/掉线会导致降不回去** |

无论哪种，都必须有**看门狗兜底**：超时未收到完成信号 → 强制 `reset_intensity`。

#### 5.9.2 强度以 **App 回报为准**，本地只做缓存

DG-LAB App 自己会**限幅**：我们发的 `+10` 可能实际只生效 `+3`。因此：

1. **每次开火后同步真实强度**（不能假定自己的意图值生效）
2. **订阅 `slots.patch` / `devices.patch` 里的真实强度（事件推送），不要轮询** —— 这是低延迟的关键
3. 本地维护"最近已知真实强度"缓存，判定引擎**按真实值决策**，不按意图值

#### 5.9.3 App 的两级上限，且会动态变化

App 的逻辑（用户确认）：

- 有 **舒适上限** 和 **强度上限** 两级
- **超过舒适上限一段时间 → 自动降到舒适上限**
- **上限本身还随使用时间动态调整**

对我们的影响：

- ❌ **不要硬编码上限**（比如把 100 当可用上限）—— 上限是**运行时状态**
- ❌ 不要把"我设了 50"当成"现在就是 50"
- ✅ 开火前用**真实强度 + 目标强度**对照当前上限；超了就按上限算（或先询问）
- ✅ 所有上限/强度都从 App 的 `props` / 事件里读

#### 5.9.4 延迟要求

开火链路本身很短（本地 Zenoh → V4 一跳），但"每次开火都查一次强度"会把延迟翻倍。
所以用 **事件驱动的强度缓存**（§5.9.2 第 2 条），而不是"开火前 `request_devices` 同步一次"。

> **落地位置**：`agent/nodes/coyote_v4/`（fire 的强度语义 + 强度缓存）与 `agent/nodes/rules/`（按真实强度决策）。
> T4 任务书已同步新增 §6.2。

## 七、安全职责（按你的决定：交给 DG-LAB App）

本项目**不实现**限幅/限步/看门狗/急停等安全层。原参考实现 `Safety.kt` 仅作背景知识，不进代码。

为了让 App 的审查结果能如实落到硬件上，我们只遵守一条工程纪律：

> **桥接层原样转发，不放大、不篡改数值。** App 算出多少强度、什么波形，就传多少 —— 这样 App 的安全审查才是有效的。

链路中 App 审查的生效位置（排障用）：
- 控制端 App ↔ 模拟郊狼：App 侧的强度上限/变化限制作用于它下发的 `B0`
- 被控端 App ↔ 真实主机：被控者 App 自身的上限约束最终生效
- 我们两端都只做协议转译与转发

> ⭐ **P1 是第一批实现目标**：打通模型/性能/传输/渲染四环，是最小可验证闭环。

## 十、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **Windows BLE peripheral（模拟郊狼）兼容性** | 需求 8 路线 A 可能不可行 | P2 先做最小验证（能否被手机 App 搜到并连接）；失败转 ESP32 |
| ~~mediapipe 在 Python 3.13 可用性~~ | ~~P1 卡住~~ | ✅ **已排除**：P0 实测通过，见 §6.1 |
| `B0` 100ms 高频流跨网转 V4 | 带宽/抖动 | 桥接层做波形聚合（V4 `AppendPulseData` 支持批量+时长），降频下发 |
| MediaPipe CPU 占用 | 抢资源 | 降采样 480p/15FPS；Pose 与 Face 交替推理 |
| "淫叫/求饶"非语义声音识别 | 需求 1e 效果 | 音量分级 + 音高/频谱特征（参考 Coyote-in-Cradle 成熟做法），ASR 作增强 |
| 樱花穿透稳定性/备案 | 需求 7 | frpc 断线重连；备用端口 + M-B 中继兜底 |
| WebRTC 需 STUN/TURN | M-C | 先跑 M-A/M-B；确需再自建 coturn |

**手机采集端候选**（需求 6）：`MediaMTX`（手机推流 PC 拉流，现成稳定）／自研 Android App（CameraX + WebSocket 推 JPEG 序列，与 M1 直连）／现成 App（零开发不可控）。

## 十一、已拍板的决策

| # | 决策 | 结果 |
|---|---|---|
| 1 | 需求 8 硬件路线 | **A 先验证 Windows 纯软件 BLE 外设，失败再转 ESP32** |
| 2 | 传输架构 | **WebRTC DataChannel 真 P2P**（作为 M-C 增强；先跑 M-A/M-B） |
| 3 | 第一批实现 | **P0 环境 + P1 姿态 MVP** |
| 4 | 部署拓扑 | **控制者 PC = 模拟郊狼 + 控制服务端；被控者 PC = 被控服务端** |
| 5 | 对称性 | **整条链路 ×2 且可反向**，A/B 都能当控制或被控 |
| 6 | 被控郊狼接入 | **socket v4**（被控侧）；控制侧走**模拟蓝牙郊狼** |
| 7 | 判定位置 | **控制端判定 → 被控端纯执行** |
| 8 | 安全设计 | **不做；由 DG-LAB App 自身安全审查承担** |
| 9 | 节点中间件 | **Zenoh**（ROS2 官方选定的非 DDS 中间件，`eclipse-zenoh` 已验证可装） |
| 10 | 架构形态 | **按功能细切节点**（12 个独立进程）→ 可复用 + 故障隔离 |
