### 4.4 V4 操作方法（**开火就用 `send_pulse`**）

| 方法 | 说明 |
|---|---|
| `request_devices(client_id)` | 请求设备列表 → 拿 `slotId` |
| **`send_pulse(client_id, slot_id, channel, duration, frames, options=None)`** | **下发波形 = 开火** |
| `clear_pulse(client_id, slot_id, channel)` | 清理该通道全部任务 |
| `clear_operate(client_id, options=None)` | 清理全部/指定设备/指定通道 |
| `reset_intensity(client_id, slot_id, channel)` | 强度归零 |
| `add_intensity(...)` / `reduce_strength(...)` | 增减强度 |
| `set_temp_intensity(client_id, slot_id, channel, value, duration)` | 临时强度（ms） |
| `ping(client_id)` | 返回 App 本地时间戳 |
| `send(client_id, data, options=None)` | 自定义 V4 请求 |

`channel` 用 `V4Channel.A` / `V4Channel.B`（或 `0` / `1`）。
`frames` 接受 `list[str]`（十六进制帧）或 `list[list[int]]`。

### 4.6 波形导入（⭐ 用户明确要求：**V2 / V3 两种格式都要能导入**）

#### 4.6.1 两种帧格式的规格

**V3 帧（推荐）—— 每帧 8 字节 = 16 个 hex 字符**，4 组 (频率, 强度)，每组 25ms，合计 **100ms/帧**
```
"0A0A0A0A64646464"
 └─频率×4─┘└─强度×4─┘
频率 10~240（若上游是 10~1000，按蓝牙协议换算）；波形强度 0~100
```

**V2 帧 —— 每帧 3 字节 = 6 个 hex 字符**，小端 24 位**位打包**，同样 **100ms/帧**
```
bit  4..0  = X   (5 bit)
bit 14..5  = Y  (10 bit)
bit 19..15 = Z   (5 bit)
bit 23..20 = 保留
```
依据：`reference/dglab-bluetooth-protocol/coyote/v2/README.md` 的 `PWM_A34` / `PWM_B34` 位域定义。

实机对照（来自官方 `coyote/v2/example.md`）：
```
x=1, y=9, z=0   → V2 "210100"   → V3 "0A0A0A0A00000000"
x=1, y=9, z=20  → V2 "21010A"   → V3 "0A0A0A0A64646464"
```
> 校验方法：`"21010A"` 按**小端**解读为 `0x0A0121` = 655649，
> `>>0 & 0x1F` = 1 (X)、`>>5 & 0x3FF` = 9 (Y)、`>>15 & 0x1F` = 20 (Z) ✅

#### 4.6.2 官方测试向量（**必须拿来写单测**）

`reference/dglab-websocket-simple/socket/DG_WAVES_V2_V3_simple.js`（1516 行）含 **16 条**波形，
每条**同时**给出 `raw` / `expectedV2` / `expectedV3` 三种表示：

```
呼吸 · 潮汐 · 连击 · 快速按捏 · 按捏渐强 · 心跳节奏 · 压缩 · 节奏步伐
颗粒摩擦 · 渐变弹跳 · 波浪涟漪 · 雨水冲刷 · 变速敲击 · 信号灯 · 挑逗1 · 挑逗2
```

> ⭐ **这是官方给的"标准答案"** —— 解析 V2/V3 后与 `expectedV2`/`expectedV3` 比对；
> 若实现格式转换，V2↔V3 互转也必须对得上。**这是本任务质量的关键保证。**

#### 4.6.3 识别与校验规则

1. **按帧长度自动识别**：6 hex → V2；16 hex → V3
2. **同一条波形内帧长必须一致**，混用直接报错（**不要猜**）
3. **时长适配**：`duration_ms` 与帧数不符时（每帧 100ms），循环补齐或截断
4. **字符校验**：非法 hex、奇数长度 → 报错并**指出是第几帧**

#### 4.6.4 支持导入的文件格式

**A. JSON（推荐）**
```jsonc
{
  "name": "我的波形",
  "version": 3,                          // 可省，省略则自动识别
  "frames": ["0A0A0A0A00000000", "..."]
}
```

**B. 纯文本（每行一帧）**
```
# 支持注释与空行
0A0A0A0A00000000
0A0A0A0A14141414
```

> 可选扩展：官方 `raw` 格式（波形设计器导出）
> `Dungeonlab+pulse:35,1,8=0,20,0,1,1/0-1,20-0,40-0,...`
> 用户只要求 V2/V3 两种，这个**列为可选** —— 做了加分，不做不扣分。

#### 4.6.5 存储与合并

- 导入的波形存 `data/waveforms/<name>.json`
- 启动时加载，与 SDK 官方波形**合并成一张查找表**
- **官方波形优先**；重名时给出提示（不要静默覆盖）

#### 4.6.6 下发时必须带版本号

`send_pulse` 的 `options` 里带 `ver`：**V2 帧传 `2`；V3 帧传 `3` 或省略**。
依据 `reference/dglab-kit/src/socket/v4/types.ts` 的 `V4AppendPulseDataOptions.version`：
> `version`：波形数据版本，**2 表示 V2 帧，省略或 3 表示 V3 帧**

## 5. ⚠️ 手动传输模式 —— **未采用**（2026-10-04 协调者定：改走直连对端 relay）

> **决定**：**不用**手动传输模式。
> 原因：那条路的帧要走 `command/raw_v4`，而 T3 的 bridge 白名单把它列为**永不跨机** ——
> 帧根本到不了对端；单机又没有组件扮演 V4 服务器（先发 hello 帧，SDK 才拿得到 `targetId`），
> 于是只会一直 `connect_timeout`。
>
> **改用直连**：`coyote_v4` 连**对端 relay**（被控端跑 `python tools/relay.py`），
> 地址配在 `agent/config.toml` 的 `[coyote_v4] url`（模板见 `agent/config.example.toml`）。
> 这条路**已实测跑通**（连上后拿到 `targetId`）。
>
> 下面是原设计，仅作背景保留。

我们的传输层 **不是**直连 `ws://…:9998`，而是走自己的 `room`/`transport`（中继或 WebRTC）。

SDK 为此提供了**手动传输模式** —— 不传 `url` 构造，然后自己喂数据：

```python
socket = DglabSocket(version=DGLAB_SOCKET_VERSION.V4)   # 不传 url

# 注册发送器：SDK 要发数据时，调用这个函数，我们负责送到对端
def sender(data):            # data 是文本或二进制
    asyncio.create_task(room.send_raw_to_coyote(data))

socket.set_sender(sender)    # 或 setSender(...)

# 收到对端数据时，喂给 SDK
socket.handle_message(data)  # 或 handleMessage(...)
# 同理还有 handle_open / handle_close / handle_error
```

**这是本任务最有技术含量的部分**：把 V4 的 WebSocket 语义**桥接到我们的房间消息**上。

> 实现要求：
> 1. 在 `transport_adapter.py` 里统一封装：`set_sender` → `room.send(type="coyote_v4_raw")`；收到该类型 → `socket.handle_message(...)`
> 2. 保持帧**原样透传**（不要解析再重组），因为 SDK 自己会解析
> 3. 断线时记得 `socket.handle_close(...)`，让 SDK 状态机正确迁移

## 6. 对外接口（供 bridge / 判定引擎调用）

```python
# agent/controlled/coyote_v4/__init__.py
class CoyoteV4Controller:
    def __init__(self,
                 transport=None,          # None → 直连模式；否则用手动传输模式
                 url: str | None = None,  # 直连模式用
                 on_action: Callable[[dict], None] = None,   # App 动作反馈（反控）
                 on_devices: Callable[[list, str], None] = None,
                 ): ...

    async def start(self) -> str:
        """连接并返回 targetId（配对用）。"""

    @property
    def pairing_url(self) -> str:
        """生成 App 扫码用的配对链接（见 §7）。"""

    async def wait_for_peer(self, timeout: float = 120) -> str:
        """等待 App 接入，返回 client_id。"""

    async def fire(self,
                   waveform: str,                 # 如 "PULSE" / "TEASE_2"
                   channel: str = "A",
                   duration_ms: int = 2000,
                   priority: int = 0,
                   overlay: bool = True,
                   client_id: str | None = None) -> None:
        """开火一个波形。overlay=True → 叠加（不抢占）。"""

    async def stop(self, channel: str | None = None) -> None:
        """急停：clear_pulse / clear_operate。"""

    @property
    def is_paired(self) -> bool: ...
```

**`fire()` 的语义**（需求原文：惩罚 = 特定波形开火）
1. 找到目标 `client_id`（默认最近接入的那个）与 `slot_id`（来自 `request_devices`）
2. 用 `COYOTE_WAVEFORMS[waveform]["raw"]` 取帧
3. 若 `duration_ms` 与帧自然长度不符 → 循环补齐/截断（⚠️ **这段适配要自己写**，SDK 不做）
4. 调 `send_pulse(..., duration, frames, options)` 下发
5. `options` 里带 `priority` 与 `im`（`overlay=True` → `im=False`）

### 6.2 ⚠️ 强度语义（**真机反馈，必须按这个做**）

> 参考框架文档 §5.9。**当前实现只做了一半**：`add_intensity(+N)` 加完就不管了 —— 不符合真实玩法。

#### (1) 开火有"时长"，**结束时强度必须降回去**

一次开火 = **临时提强度 + 播波形**，时长到了就恢复。否则强度会一直停在 N，下次越堆越高。

- **首选**：`set_temp_intensity(client_id, slot_id, channel, value, duration_ms)`
  （V4 动作码 `SetTempIntensity=4`，App 侧自动回落）→ **要实测它与波形并发时的行为**
- 备选：自己 `add(+N)`，`duration` 后定时 `add(-N)` → 必须带**看门狗**（超时强制 `reset_intensity`）

#### (2) 强度**以 App 回报为准**，本地只做缓存

App 会**限幅**（发 `+10` 可能实生效 `+3`），所以：

- 每次开火后**同步真实强度**，不能假定意图值生效
- **订阅 `slots.patch` / `devices.patch` 的真实强度（事件推送）**，**不要轮询** ← 低延迟的关键
- 本地缓存"最近已知真实强度"；判定引擎按**真实值**决策

#### (3) App 的**两级上限**且**动态变化**（❌ 不要硬编码）

- 有 **舒适上限**、**强度上限** 两级
- **超舒适上限一段时间 → 自动降到舒适上限**
- **上限随使用时间动态调整**

→ 上限是**运行时状态**：从 App 的 `props` / 事件里读，不要写死数字；开火前用
"真实强度 + 目标值"对照当前上限。

#### (4) 验收补充（加到 §8）

| # | 标准 |
|---|---|
| **D18** | 开火带 `duration_ms`，**结束后强度回到开火前的值**（真机量测） |
| **D19** | 强度**以 App 回报为准**：发 `+10` 而 App 只给 `+3` 时，本地缓存的也是 `+3` |
| **D20** | 强度缓存由 **事件驱动**（`slots.patch`），**不是每次开火都 query** —— 延迟不因同步而翻倍 |
| **D21** | 不硬编码上限：App 上限变化后，下一次开火按**新的**上限判断 |

## 7. 配对二维码

SDK 只返回 `targetId`，**二维码要自己按 `dglab-kit` 的规则拼**：

```
wsUrl  = wss://<你的地址>/v4?tid=<targetId>
```

## 9. 风险与对策
