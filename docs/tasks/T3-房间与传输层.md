# 任务 T3：跨机桥接（`bridge` 节点）

> ⚡ **v3 重大变更：Zenoh 接管了大部分原计划工作**
>
> 原计划自研"房间 + 三种传输 + 加密"。改用 **Zenoh** 作中间件后，**跨机连通、自动发现、链路加密（TLS/mTLS）都由 Zenoh 提供**。本任务范围收缩为：
>
> 1. **`bridge` 节点**：白名单转发 —— 🔒 **`feature/frame.raw` 与 `command/raw_v4` 永不跨机**（需求 1d 的代码级落地）
> 2. **房间语义**：房间码、角色协商、建房/加入流程
> 3. **应用层 AEAD（可选）**：Zenoh TLS 只是链路加密；若需**端到端**（中继也看不到），再加一层
> 4. **中继**：双方都在 NAT 后无法直连时，用 Zenoh **router 模式**（`zenohd`）做中继
>
> - 路径：**`agent/nodes/bridge/`**（下文若见 `agent/room/`、`agent/transport/`、`agent/relay/`，按此对照）
> - **下文 §4（信封协议）、§6（接口）的设计大部分仍然适用** —— 它们现在是**跑在 Zenoh 之上的一层应用协议**；
>   但"自研 WebSocket 传输"那部分已被 Zenoh 取代，请按上面的收缩范围理解
> - 必须继承 `agent/core/` 的 `Node` 基类

> **交付方**：任意 AI agent（可独立开工）
> **上位文档**：`docs/架构设计与路线图.md`（第三章拓扑、第五章 M6）
> **优先级**：**P3** —— `FeatureFrame` 与郊狼指令都要靠它过河
> **预估**：2~3 天
> **依赖**：无（可与其他任务并行；接口按本文件的契约写即可）

## 0. 一句话目标

让 A、B 两端能**建房间、互相认出来、加密地双向传消息**，并支持用户指定的**两种连接方式**：

| 模式 | 做法 |
|---|---|
| **M-A 直连** | A 端建房并监听端口 → 樱花 frp 暴露 → B 端凭房间码接入（**不经第三方**） |
| **M-B 中继** | A、B 都连到同一台公共服务器，凭房间码配对（服务器只转发**密文**） |

外加可选的 **M-C：WebRTC DataChannel 真 P2P**（用户先前的选择，作为增强，不阻塞前两个）。

**关键设计前提**：两端跑的是**同一份程序**，角色（控制方/被控方）由房间协商决定，**可互换**。

## 4. 信封协议（本任务的核心契约）

### 4.1 信封结构

```jsonc
{
  "v": 1,                       // 信封版本
  "room": "AB12CD",             // 房间码
  "from": "A",                  // 发送方角色标签： "A" | "B"
  "seq": 1234,                  // 单调递增序号（重放/丢包检测）
  "ts": 1719817201234,          // 发送时刻 ms
  "type": "feature",            // 见下表
  "payload": { /* 由 type 决定，本层不解释内部结构 */ }
}
```

### 4.2 类型定义

| `type` | 方向 | payload | 归属 |
|---|---|---|---|
| `hello` | 双向 | `{role, name, caps:[...], version}` | 本任务 |
| `role` | 双向 | `{self:"controller"\|"controlled"\|"both"}` | 本任务 |
| `ping` / `pong` | 双向 | `{ts}` | 本任务 |
| `bye` | 双向 | `{reason}` | 本任务 |
| **`feature`** | 被控→控制 | `FeatureFrame`（T2 定义） | **透传，本层不解析** |
| **`coyote`** | 控制→被控 | 郊狼指令（T4 定义） | **透传，本层不解析** |
| **`event`** | 双向 | 爪印/心率/开火记录等 | **透传** |
| `ack` | 双向 | `{seq}` | 本任务（可选） |

> ⭐ **分层铁律**：`room`/`transport` **绝不解析** `feature`/`coyote` 的 payload。加新消息类型不需要改传输层。

### 4.3 房间码

- `6` 位，字符集 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`（去掉易混的 `0/O/1/I/L`）
- 用 `secrets.choice` 生成，**不是**随机密钥
- 房间码 + 双方随机 nonce → `HKDF-SHA256` 派生会话密钥

### 4.4 加密

- **必须**：每条信封的 `payload` 用 **AES-256-GCM** 加密（`cryptography` 库）
- 加密范围：`payload` 的规范 JSON 序列化；`v/room/from/seq/ts/type` 作为 **AAD**（附加认证数据）保证不被篡改
- 密钥派生：
  ```
  ikm    = 房间码 + ECDH 共享密钥（推荐 X25519 交换）或 双方 nonce 拼接
  key    = HKDF-SHA256(ikm, salt=room, info="coyotelink-v1")
  ```
  > 若时间紧，最低要求：`HKDF(房间码 + 双方 nonce)`，并在文档里标注"房间码即口令，安全性依赖房间码不外泄"。**但 X25519 是明确更优的做法，建议直接做。**
- 传输层若已是 TLS/WSS，这是**应用层 E2E 加密**，二者叠加 —— 中继服务器因此看不到明文

### 4.5 有序性与可靠性

- `seq` 单调递增；接收端检测**跳号**（丢包）与**倒退**（重放），打日志
- `feature` 类消息**允许丢**（丢一帧骨骼无所谓，用最新的）
- `coyote` 类消息**不允许丢**（丢一条强度指令可能造成状态不同步）→ 需要 ACK 或至少序号连续性检查告警

## 5. 三种传输的实现要点

### M-A 直连（`direct.py`）

```
A 端（建房方）：起 WSS 服务端监听（默认 9443），等待 B 连接
B 端（加入方）：连 wss://<A的公网地址>:<端口>?room=AB12CD
```
- 用 `fastapi` + `uvicorn` 或直接 `websockets.serve`
- 自签证书即可（`cryptography` 生成），B 端允许跳过校验（因为已有应用层 E2E）
- 暴露到公网由**用户自行配樱花 frpc**（属于 T7/部署，不在本任务内，但要在 README 里写清端口）

### M-B 中继（`relay.py` + `relay/server.py`）

```
A 端 ─┐
      ├──► 公共中继服务器（只看房间码转发密文）
B 端 ─┘
```
- 中继服务器：`ws://host:9997`，收到 `{room, from, data}` 就转发给**同房间的另一个连接**
- **服务器不持有密钥、不解密** —— 这是"中继也安全"的前提，务必在代码注释和文档里写明
- 房间内最多 2 个连接；第 3 个加入报错

### M-C WebRTC（`webrtc.py`，可后补）

- `aiortc` + 信令走 M-A/M-B 的同一个 WS 通道
- 目标：`FeatureFrame` 走 DataChannel，降低延迟
- **不阻塞** M-A/M-B 的交付

## 6. 对外接口

```python
# agent/transport/base.py
from abc import ABC, abstractmethod

class Transport(ABC):
    @abstractmethod
    async def start(self) -> None: ...
    @abstractmethod
    async def send(self, envelope: dict) -> None: ...
    @abstractmethod
    async def stop(self) -> None: ...
    on_message: Callable[[dict], None]      # 收到信封（已解密）
    on_peer_state: Callable[[str], None]    # "connected" / "disconnected"

# agent/room/room.py
class Room:
    def __init__(self,
                 mode: Literal["direct", "relay", "webrtc"] = "direct",
                 role: Literal["controller", "controlled", "both"] = "both",
                 relay_url: str | None = None): ...

    @classmethod
    def create(cls, **kw) -> tuple["Room", str]:
        """建房，返回 (room, 房间码)"""

    @classmethod
    async def join(cls, code: str, peer_addr: str, **kw) -> "Room":
        """加入已有房间"""

    async def start(self) -> None: ...
    async def send(self, type: str, payload: dict) -> None:
        """发送一条消息（自动加密 + 编号）"""

    async def stop(self) -> None: ...

    # 回调
    on_message: Callable[[str, dict], None]   # (type, payload) —— 已解密、已验号
    on_peer_state: Callable[[str], None]

    @property
    def peer(self) -> dict:
        """对端信息：角色、名称、地址 —— 供"看到谁访问了"用"""
```

## 7. 验收标准

| # | 标准 | 怎么验 |
|---|---|---|
| C1 | 两台机器（或同机两个进程）一个建房、一个凭 6 位码加入，**握手成功** | 跑起来 |
| C2 | A 发 `feature`，B 收到内容一致 | 单测/手动 |
| C3 | **抓包看到的是密文**，看不出 `FeatureFrame` 内容 | ⭐ Wireshark 或中继端打日志 |
| C4 | M-B 模式下，**中继服务器日志里无明文**（只有房间码和密文长度） | 看服务器日志 |
| C5 | 篡改 `payload` 或 `seq` → 接收端**拒绝**（GCM 认证失败） | 单测 |
| C6 | 角色可协商与互换：A 声明 `controlled`、B 声明 `controller` 都能跑 | 手动 |
| C7 | 一端断线，另一端 `on_peer_state("disconnected")` 触发 | 拔网线/杀进程 |
| C8 | `coyote` 类消息丢失时**有告警**（seq 跳号） | 单测 |
| C9 | 重放旧信封 → 被判为非法（seq 倒退） | 单测 |
| C10 | 同机 5 次连断不泄漏端口/连接 | 反复跑 |

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 樱花穿透配不好 | 传输层**与穿透解耦** —— 本任务只管监听/连接，frpc 由用户配；先在同机/局域网验证 |
| 自签证书被拒 | 允许 `verify=False`（已有应用层 E2E），但要在文档里写明理由 |
| NAT 后直连不通 | 这正是 M-B 中继存在的意义；M-A 只在有穿透时用 |
| `aiortc` 安装失败（依赖重） | M-C 是可选增强，**不要让它阻塞交付** |
| 房间码被猜到 | 6 位 31 字符集 ≈ 8.9 亿组合；再加"错误房间码直接断开 + 速率限制" |
